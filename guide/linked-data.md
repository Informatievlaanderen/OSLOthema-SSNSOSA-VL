# Linked data: IRIs, vocabularies, profiles and validation

Rules that hold for any RDF project. SSN/SOSA-specific rules are in [`ssn-sosa.md`](ssn-sosa.md).

## R10 — IRI construction

- **Production data:** use the authoritative base IRI of the domain (e.g.
  `https://www.dov.vlaanderen.be/data/filter/`).
- **Illustrative instances:** use sub-paths of `https://example.org/` with meaningful local names
  (e.g. `https://example.org/<domain>/…`). Not `example.com`.
- **Never use blank nodes for resources that must be referenced from outside** by IRI.
- **Large datasets** (generated by a script, many observations): give nested resources a
  deterministic *skolem IRI* instead of a blank node as well: `time:Interval`, `time:Instant`,
  results (`qudt:QuantityValue`) and `geo:Geometry`. Derive the IRI from the parent
  observation or station, e.g. `ex:interval-{obs-id}`, `ex:instant-{obs-id}-begin`,
  `ex:result-{obs-id}`, `ex:geom-{station}` (a geometry may be shared per station). Blank nodes are
  hard to query in SPARQL and join badly across graphs. In small hand-written examples an inline
  blank node is fine.
- **Exception:** when describing an *external* dataset (one you do not own), do not invent IRIs in
  someone else's namespace; a blank node is acceptable there.
- **Stable IRIs in pipelines.** A script or pipeline derives each IRI from a deterministic key
  (an identifier from the source, or a hash of the fields that identify the resource), never from a
  random value such as `STRUUID()` or `UUID()` per run. A random IRI changes at every run: other
  resources cannot refer to it, and a version chain (`dct:isVersionOf`) points to a new base IRI
  each time. Example: a sensor IRI `…/sensor/{MD5(device id)}`, which the observations can build
  from the same field.
- **Do not mint resources in a vocabulary's namespace.** A data file must not describe new
  resources in a namespace that a loaded vocabulary owns (e.g. `unit:EUR a qudt:Unit`, or a
  building in the namespace of a building ontology). Use an IRI of your own or an existing term.

### `http` versus `https`, `#` versus `/`

The identifier of a vocabulary term is exactly the IRI its publisher defines. Many sites redirect
`http` to `https`, but that does not make the `https` form the identifier: `http://qudt.org/schema/qudt/Unit`
is the term, `https://qudt.org/schema/qudt/Unit` is not. The same goes for a namespace ending in
`#` versus `/`. Check the prefix declaration first: one wrong `@prefix` breaks every term that uses
it.

## Prefixes

- Declare every prefix the file uses, and only those.
- Use the conventional prefix for a namespace (the project profile lists the project's prefixes;
  [prefix.cc](http://prefix.cc) records the common ones). A prefix that conventionally means
  something else (e.g. `geo:` for WGS84 instead of GeoSPARQL) confuses readers and tools.
- Distinguish a vocabulary's *schema* namespace from its *data* namespaces (e.g. `qudt:` for
  `qudt:hasUnit`, `unit:` for `unit:M`).

## R15 — Align classes without SKOS relations

Do not use SKOS relations between classes (`skos:broader`/`narrower`/`related`,
`skos:exactMatch`/`closeMatch`/`broadMatch`/`narrowMatch`/`relatedMatch`). A class is not a
register term. Align classes with `rdfs:subClassOf` or OWL axioms, or not at all (at most
`rdfs:seeAlso` as a pointer). The counter-example is OGC HY_Features: one IRI as both `owl:Class`
and `skos:Concept`, with the hierarchy expressed only through `skos:broader`.

- SKOS relations belong between *concepts* in code lists (e.g. a register unit
  `skos:exactMatch` a QUDT unit, see R3).
- SKOS documentation properties (`skos:definition`, `skos:scopeNote`, `skos:note`,
  `skos:example`) may be used on classes: SKOS Reference §7.5.1 gives them no domain.

## Code lists and registers

- Model code lists as SKOS concept schemes.
- **Reuse existing registers and code lists before making new ones**; make a new list only for
  values that no register covers, and only when the mapping actually needs it.
- Data refers to concept IRIs; it does not copy or extend the register. Statements *about* a
  register's concepts (labels, mappings) belong in the register. A missing concept or mapping is a
  point for the register's maintainers, not something to add in the data.
- Large registers do not belong among the data examples. When a local extract is needed (for
  documentation or JSON-LD framing), keep it out of the validated data (e.g. as `.trig`). A small
  register that the data must be checked against (e.g. a unit list) may be loaded as a vocabulary.
- Reuse existing IRIs of external datasets; refer to IRIs that are not yet final with
  `rdfs:seeAlso`.

## R18 — Type with a concept or with a class

The core vocabularies are abstract: a `sosa:System`, a `prov:Entity` or a `p-plan:Step` says
nothing about the domain. The domain's own kinds (an air scrubber, a discharge point, a manhole, an
ingredient) enter the model in one of two ways:

- **as a concept:** the resource keeps a general class and gets `dct:type` to a `skos:Concept` in
  a code list;
- **as a class:** a subclass of a core class of your own (`rdfs:subClassOf`), used with `rdf:type`.

**The test: does the kind have rules of its own?** Make it a class when it has properties,
cardinalities, value restrictions or inferences of its own: something that holds for its members
and not for the other members of the general class. Otherwise make it a concept. A kind that only
names, groups or filters is a concept.

**The two combine.** A class for each kind with rules of its own, and a concept for the finer kinds
within it:

```turtle
riepr:Emissiepunt rdfs:subClassOf sosa:System ;          # own restrictions: geometry, properties, …
    rdfs:subClassOf [ a owl:Restriction ; owl:onProperty dct:type ; owl:allValuesFrom skos:Concept ] .

riepr:Emissieproces rdfs:subClassOf riepr:Proces ;       # own rule: which kind of system runs it
    rdfs:subClassOf [ a owl:Restriction ;
        owl:onProperty sosa:implementedBy ; owl:someValuesFrom riepr:Emissiepunt ] .

ex:lozingspunt-LP01 a riepr:Emissiepunt , sosa:System ;
    dct:type emissiepunt-type:lozingspunt .                 # finer kind, no rules of its own
ex:lozing-LP01 a riepr:Emissieproces , riepr:Proces , p-plan:Step ;
    sosa:implementedBy ex:lozingspunt-LP01 .
```

**The model decides the code list.** A model with only abstract classes needs a code list with
every kind (installation, emission point, measuring point, …). A model with subclasses no longer
needs those kinds as concepts, only the finer ones within each class. Decide the classes first;
the code list follows. A code list that repeats the classes says the same thing twice, and the two
drift apart.

**Signs that a concept should be a class:**
- an axiom or shape hangs a rule on a value of `dct:type` (`owl:hasValue` inside an
  `owl:intersectionOf`, a SHACL target on a value). That is a subclass in disguise. The generator
  of ld-mcp does not translate an axiom on an anonymous class, so the rule goes unchecked; as a
  restriction on a named subclass it becomes a shape;
- the ontology copies concepts of a code list into its own namespace to hang rules on them
  (`:emissieProcedure a sosa:Procedure, skos:Concept ; skos:related <concept in the code list>`);
- the definition of a concept states a rule ("emission through an emission point").

**Signs that a class should be a concept:** a subclass without restrictions of its own, which only
renames (`riepr:ZuiveringsApparaat` beside `riepr:Installatie`: an air scrubber has no rules that
another installation lacks).

**`dct:type` and its range.** DCTERMS gives `dct:type` the range `rdfs:Class`, so a concept as its
value is formally also a class. Practice (OSLO, DCAT-AP) uses concepts all the same, and validation
reports no inconsistency. A profile that wants to avoid the inference uses a subproperty of
`dct:type` of its own with range `skos:Concept`. Never a literal: `dct:type "Overflow meter"` is
not a type. In a profile, restrict the value with `owl:allValuesFrom skos:Concept`; the generated
SHACL cannot say *which* code list, so document the scheme in a comment.

**Not a type.** A concept as the value of a role is not a typing: a `csor:ParameterAspect` as
`sosa:observedProperty` is the property itself, an individual. A class whose members are concepts
with rules of their own (`csor:ParameterAspect ⊂ sosa:Property`, `riepr:Rubriek ⊂ skos:Concept`,
with a required `skos:notation`) follows the same test.

In OSLOthema-SSNSOSA-VL: `riepr/` (kinds of process as subclasses, installation and emission point
types as concepts), `waterkwaliteit/` (`wk:Emissie` as a class, emission type and matrix with
`dct:type`), `Nigella-Lawson-Brownies/` (an abstract model, every ingredient a concept).

## R17 — Choose vocabularies deliberately

A term outside the core is the outcome of a comparison, not of the first search hit. Cherry-picking
terms from whatever vocabulary happens to be loaded or found leaves the data with commitments
nobody chose (a domain that types your sensor as something else, a namespace that disappears).

**Order of preference.** Use a term from a later level only when the earlier levels cannot express
the meaning:

1. the core already loaded: SOSA/SSN, PROV-O, QUDT, OWL-Time, GeoSPARQL, SKOS, DCTERMS, RDFS;
2. other W3C and OGC models;
3. government vocabularies and registers: OSLO (data.vlaanderen.be), the SEMIC Core Vocabularies,
   the registers named in the project profile;
4. standards from other bodies (ISO, ETSI);
5. anything else.

**LOV is for exploring, not for selecting.** [Linked Open Vocabularies](https://lov.linkeddata.es)
shows candidate terms and the contexts in which others use them. Its ranking is textual: a search
for `Sample` puts `sp:Sample` (SPIN, a SPARQL vocabulary) level with `sosa:Sample`, and its reuse
metrics are not reliable. A hit is a candidate, never a recommendation.

**schema.org only as a last resort.** schema.org serves web markup for search engines, not data
models, and that shows in the criteria below:
- the term IRIs return HTML on content negotiation (1); RDF is available only as release
  downloads;
- `http://schema.org/` and `https://schema.org/` are both in use for the same terms (2);
- it is not aligned with PROV-O or SOSA except through the preliminary module `sosa-sdo` of
  SSN/SOSA 2023 (8).

Prefer a term from levels 1–4; when schema.org is the only candidate, say why in the discussion.

**Criteria.** Assess every candidate vocabulary on:

| # | Criterion | What to check |
|---|---|---|
| | *Technical* | |
| 1 | Dereferenceable as RDF | the namespace and a sample term return RDF (Turtle, RDF/XML or JSON-LD) on content negotiation; an HTML page or a JSON-LD `@context` alone is not enough (see Validation) |
| 2 | Persistent namespace | w3id, purl or the domain of a standards body; `http` and `https` used consistently |
| 3 | Versioned | `owl:versionIRI` or `owl:versionInfo`, a change log, withdrawn terms marked `owl:deprecated` |
| 4 | Licence | explicit and open |
| 5 | Formally sound | terms typed, with labels and definitions; where a domain or range is declared, it makes sense (a missing `rdfs:domain` is often a deliberate choice, as in DCTERMS and SSN/SOSA 2023, to keep a property reusable and avoid unwanted inferences); no SKOS between classes (R15); no axioms about other vocabularies' terms (`sosa:`, `prov:`, …) |
| 6 | Consistent with the core | once loaded, the existing examples still give no `[DISJOINTNESS]` violation (R16) |
| | *Semantic* | |
| 7 | Fit with the domain | judged on the *definition*, not the label; abstract vocabularies (PROV, SKOS, DCTERMS) are welcome where their definition fits |
| 8 | Aligned with the core | `rdfs:subClassOf` / `rdfs:subPropertyOf` to SOSA or PROV, or at least nothing that conflicts with them. Search as described under *Finding alignments* below |
| 9 | Commitment | what the domain, range and inferences of the one term you need add to the data, read together with the alignment (8): e.g. the domain of `saref:hasManufacturer` makes the subject a `saref:FeatureOfInterest`, which the SOSA–SAREF alignment already makes every `sosa:System` |
| 10 | Granularity | not tied to one project or application |
| | *Governance* | |
| 11 | Publisher | a standards body, a government or an active community, rather than a finished research project |
| 12 | Maintenance | recent release, an issue tracker that is used |
| 13 | Adoption | used in the target community (OSLO, SEMIC, INSPIRE, datasets) |
| 14 | Labels in the project language | present, or possible to add |
| | *Proportion* | |
| 15 | Worth it | one term from a large vocabulary must be worth the commitments it brings; when in doubt, add no vocabulary |

**Finding alignments.** An alignment is a statement about two vocabularies and may be published by
either, or by neither: the SOSA–SAREF alignment is a separate module of SSN/SOSA 2023
(`http://www.w3.org/ns/sosa/saref`), not part of SAREF; the SOSA namespace document does not point
to it, and LOV does not record it. Absence in the candidate is therefore not absence. Search, in
this order:

1. the register of known alignments, [`../registers/alignments.ttl`](../registers/alignments.ttl);
2. the candidate itself (links to the core);
3. the specification and repository of each core vocabulary (for SSN/SOSA 2023: chapter 7 and
   `ssn/rdf/ontology/alignments/` in `w3c/sdw-sosa-ssn`);
4. the candidate's own extension modules and documentation;
5. a code search for files that use both namespaces (e.g. `gh search code` on both namespace IRIs).

State in the discussion (§6) where you searched and what you found, so that a missing alignment is
an established absence, not an oversight. Load a module the mapping relies on, together with what it
imports, and validate all examples again. Add every alignment found to the register.

**Way of working.** A vocabulary is used only after it is loaded in the project's ontology
directory, with its source and version, and after `validate_file` on all examples is still
consistent.

**Account for it.** For every term outside the core, the discussion (§6) has a subsection *Why this
vocabulary?*: the candidates considered (including LOV hits), the assessment on the criteria that
decided, and the rejected alternatives. That makes cherry-picking visible.

## Ontologies and application profiles

**One source.** Write the ontology and the constraints of the application profile in one OWL file;
generate the SHACL from its restrictions. No hand-maintained SHACL beside it.

| OWL restriction | Generated SHACL (ld-mcp 0.4.1) |
|---|---|
| `owl:someValuesFrom C` | at least one value is a C: a property shape of its own with `sh:qualifiedValueShape [ sh:class C ]` and `sh:qualifiedMinCount 1` (other values may be anything) |
| `owl:allValuesFrom C` | `sh:class C` (or `sh:datatype`, `sh:nodeKind sh:Literal` for `rdfs:Literal`) on every value, not required |
| `owl:cardinality` / `minCardinality` / `maxCardinality n` | `sh:minCount` / `sh:maxCount` |
| `owl:minQualifiedCardinality` / `maxQualifiedCardinality` / `qualifiedCardinality` (`owl:onClass`, `owl:onDataRange`) | `sh:qualifiedValueShape` with `sh:qualifiedMinCount` / `sh:qualifiedMaxCount` |
| `owl:hasValue v` | `sh:hasValue v` |
| `owl:unionOf ( A B )` as value | `sh:or ( [sh:class A] [sh:class B] )` |
| restrictions inside `owl:intersectionOf` (also within `owl:equivalentClass`) | translated per member |
| `owl:minCardinality 0` on a property | a convention of the generator, not OWL: cancels every lower bound on the same class and property (`someValuesFrom`, the minimum of a (min)cardinality, a qualified minimum); maxima and value constraints stay. Put it on the class that carries the restriction (also a reused one, e.g. `qudt:Unit` for register units): on a subclass it cancels nothing. A cancelled `someValuesFrom` leaves no class check either; add an `owl:allValuesFrom` for that |
| anonymous property with `owl:inverseOf` | `sh:inversePath` |

The generator reads the restrictions as requirements on the data (a profile reading; OWL itself
never makes an absent value an error). Plain restrictions of a class on the same path merge into one
property shape (largest minimum, smallest maximum); identical restrictions give one constraint.
What it cannot translate (a union with an anonymous member, `owl:complementOf`, `owl:oneOf`,
property chains) it skips, never making the shape stricter, and lists in the configuration line of
the report and in the header of `generate-shapes`.

**Constrain your own subclasses, never reused classes.** A restriction on `sosa:Observation`
applies to every SOSA dataset and every other profile that reuses SOSA. Put the profile's
constraints on subclasses of your own (e.g. `wk:WaterkwaliteitObservatie ⊂ sosa:Observation`);
data types both the subclass and the reused superclass explicitly. The one exception is a
*relaxation*: an `owl:minCardinality 0` that cancels a lower bound of a reused vocabulary (e.g.
QUDT's `qudt:hasQuantityKind` on `qudt:Unit`, R3) has to sit on the reused class, because on a
subclass it cancels nothing. It adds no constraint, but it does loosen the shapes for everything
validated with this ontology directory; say so in the ontology's comments and in the discussion.

**What the generator does not express:** a choice between properties ("`numericValue` or
`upperBound`"), consistency between a collection and its members, and the labels and definitions
of properties in the profile's context (`sh:name`, `sh:description`). Document these separately.

Generate a UML diagram from the ontology rather than drawing it by hand, so that it cannot drift.

## Large datasets

Validation becomes impractically slow with files of tens of megabytes. Keep the full dataset in a
file the bulk validation skips (in the OSLO projects: `<name>.trig`, Turtle content) and write a
small, representative subset (one station, one sample) as the file that is validated, usually
selected by a variable in the generating script.

## Validation

The `ld-vocab` MCP server (`validate_file`) checks one file in four steps; use it after every
change.

| Marker | Meaning and what to do |
|---|---|
| `[VOCAB] n error(s), m suspect, k hint(s)` | every finding is marked `[error]`, `[suspect]` or `[hint]`. **Fix every `[error]`**: `Unknown property` / `Unknown class` / `Unknown resource` in a loaded namespace (e.g. a non-existent unit), `Property used as class` / `Class used as property`, `Unknown datatype` (in `xsd:`, `rdf:` or a loaded namespace), `Not a datatype` (e.g. a unit as datatype), `Invalid literal`, `Resource minted in a vocabulary namespace` (R10). **Check every `[suspect]`**: a near miss (`Did you mean <http://…>?`: the IRI differs only in `http`/`https` or `#`/`/` from an existing term; take the suggested IRI, usually by fixing the `@prefix`), an unknown term in a namespace that is neither loaded nor registered (usually a typo), `Term only referenced, not defined`, `Deprecated term` (take the replacement it names). A `[hint]` says the namespace is a known vocabulary that is not loaded: the term may exist; load that ontology before deciding. |
| `[INFERENCE]` | number of triples inferred by the domain/range/subproperty rules |
| `[DISJOINTNESS] n violation(s)` | a resource in two disjoint classes after inference, following the class hierarchy (e.g. `prov:Activity` and `prov:Entity`, see R16 in [`ssn-sosa.md`](ssn-sosa.md)); the message says by which type. Only disjointness, not full OWL consistency. Fix it. |
| `[SHACL] n violation(s), m warning(s) (a of n shapes applied …)` | messages beginning with a rule number (`R2: …`) come from the rules file; fix every violation; a `[warning]` ("strongly recommended") may stay when the source lacks the information, documented in the discussion. Messages ending in "(generated from the OWL restrictions)" come from the shapes generated from the ontology. The part in brackets says how many shapes met the data: a `conforms` with few shapes applied proves little, and `no shape applies to this data` proves nothing. |

**The graph that SHACL sees.** The data, plus the class hierarchy of the ontologies, plus the
`rdf:type` that the ontologies give to terms the data only refers to (a unit, a concept). So
`sh:class` and `sh:targetClass` follow subclasses: a `sosa:ObservingProcedure` is a `sosa:Procedure`,
and a shape on `sosa:System` reaches a `sosa:Sensor`. Triples inferred by the rules (types from
domain and range) are not included: an inferred type must not fill in a property that `sh:minCount`
requires. Other SHACL engines, run on the bare data, see no hierarchy: data that types the reused
superclasses explicitly (see *Constrain your own subclasses*) stays valid there too.

**Looking terms up:**
- Look up every class, predicate and vocabulary object (including units) with `lookup_term` before
  using it; never invent a term. Use the full IRI, written out with the file's own prefixes: the
  server's prefixes may differ.
- Check domain and range: does the subject fit the domain and the object the range?
- A term marked `owl:DeprecatedProperty`/`owl:DeprecatedClass` is not used; take its replacement.
- **A documented IRI is not yet a vocabulary.** Some term sets publish an IRI per term with an HTML
  page or a JSON-LD `@context`, but no RDF description at all (no `rdf:Property`, label or definition;
  content negotiation returns HTML). Example: Smart Data Models
  (`https://smartdatamodels.org/dataModel.Environment/deviceName`). After JSON-LD expansion such an
  IRI is an RDF predicate, but it cannot be checked, so `validate_file` reports it as unknown.
  Replace it with a term from a published vocabulary, or derive a small RDF description (type,
  label, comment, `rdfs:isDefinedBy`) from the documentation and load that as a vocabulary. Watch
  for two things: the same term may have a different IRI per domain, and NGSI-LD data in
  *normalized* form puts the value in a node (`[ a ngsi-ld:Property ; ngsi-ld:hasValue … ]`), not
  directly on the predicate.
- **Existence does not prove correctness:** `qudt:value` exists, but `qudt:numericValue` is the
  right term (R3).
- Find terms with `search_terms` (by local name or label, also individuals such as units).
