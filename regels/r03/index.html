    R3 — Een resultaat met eenheid is een qudt:QuantityValue¶

    In het kort

    Een numeriek resultaat met een fysische eenheid is een qudt:QuantityValue met qudt:numericValue en qudt:hasUnit. Niet sosa:Result (verouderd), niet qudt:value. De eenheid komt uit QUDT, of uit een domeinregister (CSOR) wanneer QUDT ze niet kan uitdrukken; één keuze per voorbeeld. Een waarde onder de rapportagegrens heeft geen numericValue, maar qudt:lowerBound en qudt:upperBound.

    Waarom¶

    • De eenheid hoort bij de waarde. Niet bij de eigenschap, niet bij het datatype.
    • Een resource kan inputwaarde zijn. Afgeleide waarnemingen verwijzen naar resultaten (R7); een literal kan dat niet.
    • Het past in de kaart. sosa:hasResult ⊂ prov:generated maakt elk resultaat een prov:Entity; een qudt:QuantityValue is dat (SOSA en QUDT).
    • sosa:Result voegt niets toe: SSN/SOSA 2023 verklaart het verouderd, en het type prov:Entity volgt al uit de alignment.

    Goed¶

    ex:waarneming sosa:hasResult [
    a qudt:QuantityValue ;
    qudt:numericValue 2.4 ;
    qudt:hasUnit unit:M3
] .

# met een register-eenheid
ex:resultaat-p a qudt:QuantityValue ;
    qudt:numericValue 0.42 ;
    qudt:hasUnit csor-eenheid:E_131 .     # mg P/L; mapping naar QUDT staat in het register

# onder de rapportagegrens
ex:resultaat-pfos a qudt:QuantityValue ;
    qudt:lowerBound 0.0 ;
    qudt:upperBound 0.0125 ;
    qudt:hasUnit unit:MicroGM-PER-L .

    Fout¶

    ex:waarneming sosa:hasResult [
    a sosa:Result ;          # verouderd
    qudt:value 2.4 ;         # bestaat, maar is niet het patroon
    qudt:unit unit:M3        # bestaat niet
] .
ex:resultaat-pfos qudt:numericValue 0.0125 .   # "< 0,0125" als meting van 0,0125

    Register-eenheden¶

    • vind de eenheid in het register; het register kent de mapping naar QUDT (skos:exactMatch, skos:broadMatch); vermeld die in de bespreking;
    • zet geen SKOS-mappings in de data;
    • beschrijft de data de eenheid (met de klasse van het register), type ze dan ook qudt:Unit;
    • QUDT vraagt van elke eenheid een grootheidssoort en een dimensievector; het profiel versoepelt dat met owl:minCardinality 0 op qudt:Unit.

    Uitgewerkt in Register en QUDT.

    Een eigen klasse voor resultaten¶

    Een profiel dat een eigen klasse wil, maakt ze subklasse van qudt:QuantityValue (zoals wk:Meetresultaat), en de data typeert beide.

    In de casussen¶

    • Erosiepoel: qudt:unit → qudt:hasUnit.
    • Waterkwaliteit: CSOR-eenheden, rapportagegrens.
    • Geluidsmeetnet: één stijl, unit:DeciB_A en unit:SEC.

    R3 — Result with a unit — uit guide/ssn-sosa.md, kit 0.3.7

    For a numeric result with a physical unit, the object of sosa:hasResult is a qudt:QuantityValue with qudt:numericValue and qudt:hasUnit: a blank node in small examples, an IRI when the result must be referable from outside or in large datasets (a skolem IRI, R10).

    Do not type the result sosa:Result: SSN/SOSA 2023 declares it owl:deprecated (w3c/sdw-sosa-ssn #113, #163), and it adds nothing. sosa:hasResult is a subproperty of prov:generated (range prov:Entity), so any result is a prov:Entity already, and so not an activity, an instantaneous event or a literal (R16). A profile that needs a class of its own for its results makes it a subclass of qudt:QuantityValue; the data types both (as for other reused classes, see Ontologies and application profiles in linked-data.md).

    The numeric value is always in qudt:numericValue, never in qudt:value. qudt:value exists (so the vocabulary check does not flag it), but it is not the QUDT pattern for a numeric measurement.

    Source of the unit (qudt:hasUnit), one choice per example: - QUDT (default): unit:M, unit:MilliGM-PER-L, … - A domain register (e.g. CSOR in the Flemish environment domain), when QUDT cannot express the unit (substance-qualified such as "mg P/L", /100mL, meq/L) or when the domain has a register of its own (the project profile names it): - find the unit with search_terms; lookup_term shows the register's own skos:exactMatch/broadMatch to QUDT; mention that mapping in the discussion (§6); - do not add SKOS mappings to the data: they are statements about the register's concepts, in its namespace. A missing mapping is a point for the register's maintainers; - every value of qudt:hasUnit is a qudt:Unit (its range, and allValuesFrom on qudt:Quantifiable). Inference makes a register unit one, but SHACL sees only the asserted graph (Validation in linked-data.md): when the data describes the unit (types it with the register's class), type it qudt:Unit as well, e.g. csor-eenheid:… a csor:Eenheid , qudt:Unit. A unit the data only refers to needs no typing; - QUDT requires a qudt:hasQuantityKind and a qudt:hasDimensionVector on every qudt:Unit, which a register unit usually lacks. Do not add them to the data (they belong in the register); relax them in the profile's ontology with owl:minCardinality 0 on qudt:Unit for both properties, which makes them not required in the generated SHACL (see Ontologies and application profiles in linked-data.md).

    A value below the reporting limit ("< 0.0125 µg/L") has no qudt:numericValue: give the interval with qudt:lowerBound and qudt:upperBound (see patterns.md).
