# Alternative mapping

A revision (skill `revise-mapping`) replaces a wrong model. An **alternative mapping** stands next to
a model that is not wrong: two defensible readings of the same data, neither excluding the other.
The choice belongs to the working group, not to whoever writes the example. Do not narrow the
original reading down; the point is to keep both open.

Example (OSLOthema-SSNSOSA-VL): `geluidsmeetnet/` models a noise event as a `sosa:Stimulus` with the
monitoring station as feature of interest; `geluidsmeetnet/alternatief/` models it as an emission
and feature of interest, generated by the flight — the same pattern as the discharge in
`waterkwaliteit/`. See [`patterns.md`](../../guide/patterns.md).

## When

A modelling choice can be defended in two ways, typically when:
- the domain's natural reading differs from a pattern other examples already use (the domain's own
  character versus consistency across domains); or
- the choice is a decision point for a working group (an OSLO trajectory).

A "rejected alternative" in §6 of the discussion suffices when the alternative is clearly weaker;
an alternative mapping is for choices that are genuinely open.

## Steps

1. **Ask** which example, which choice is read differently, and which other example or pattern the
   alternative follows.
2. **Directory** inside the example: `alternatief/` in Dutch OSLO projects (project profile); with
   several alternatives `alternatief-<core>/`. It contains:
   - a README with **Intent** ("not a revision; both readings side by side for the working group"),
     the source and the selection, and a table **Differences from the main model** (aspect → main
     model → alternative);
   - the Turtle and its diagram;
   - a comparison diagram: both models side by side, focused on what differs;
   - a discussion document with the nine sections; §6 holds the arguments **for** and **against**,
     any intermediate forms, and **discussion questions** for the working group.
3. **A small, representative selection** suffices (e.g. one flight): the aim is comparison, not
   completeness. Writing it by hand is fine; say which change the generating script would need if
   the alternative is chosen.
4. **IRIs:** reuse the main model's IRIs for what is shared (`ex:`); give what differs a prefix of
   its own (e.g. `alt:`), so that both can be loaded side by side.
5. **Name the connection** explicitly: which other example or pattern the alternative follows (e.g.
   waterkwaliteit, decision document A5 and A14).
6. **Neutral:** the main model is not called wrong. Give both a status as in a decision document
   (*proposal*, *open*, *decided* with date).
7. **Refer both ways:** the main model's discussion mentions the alternative at the relevant choice
   in §6 (and in its README), and the alternative refers back.
8. **Validate** both with `validate_file`.

## After a decision

The chosen model becomes the main model (adapt the script if needed). The other stays as a
documented rejected alternative, with status *decided* and the date: why the choice was made is
knowledge too. Do not delete it. If the decision establishes a pattern, add it to
[`patterns.md`](../../guide/patterns.md).
